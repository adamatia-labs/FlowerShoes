# 탈퇴·재가입 경계와 복구

## 저장 계약

- `accountDeletions/{uid}`는 서버 전용 삭제 작업과 영구 차단 기록이다. 한 번 생긴 UID는 다시 활성 계정으로 사용하지 않는다. Firestore와 Storage 규칙은 이 문서가 있으면 해당 UID의 모든 클라이언트 접근을 거부한다.
- `kakaoAccounts/{카카오ID}`는 현재 가입 세대의 Firebase UID와 이전 탈퇴 완료 시각을 저장한다. 기존 사용자는 `kakao:<id>`를 계속 쓰며, **완료가 확인된 탈퇴 이후에 시작한 로그인**으로 재가입하면 `kakao:<id>:<무작위UUID>`를 새로 발급한다. 이전 UID나 커스텀 토큰을 새 세대에 연결하지 않는다. 탈퇴 전에 시작했다가 늦게 돌아온 로그인도 거부한다.
- 이미 발급된 Firebase 커스텀 토큰은 삭제된 이전 Auth 사용자를 다시 만들 수 있다. 따라서 Auth 삭제만으로 차단했다고 보지 않으며, 차단 기록에 TTL을 설정하지 않는다. 소셜 제공자의 이름·토큰·콘텐츠는 차단 기록에 저장하지 않는다. 최소 식별자와 처리 상태, 카카오 매핑은 서비스 운영 종료까지 보관한다. 앱의 개인정보 안내에도 이 보유 항목을 명시한다.
- 삭제 작업이 시작된 계정은 새 초대를 만들거나 수락할 수 없다. 이미 큐에 들어간 수락 이벤트와 기기 승인도 같은 차단 기록을 트랜잭션에서 확인하므로 삭제 뒤 사용자·관계를 다시 만들지 않는다.
- 카카오 로그인 경계는 외부 토큰 검증 전 Firestore의 읽기 시각과 삭제 완료의 서버 시각을 비교한다. 함수 인스턴스의 로컬 시계 차이에 의존하지 않는다.
- Apple 코드 교환이 삭제보다 늦게 끝나면 토큰을 저장하지 않고 바로 폐기를 시도한다. 진행 중이거나 결과가 불확정인 코드 교환이 있으면 수동 연결 해제 안내를 반환한다. 토큰을 지우기 전에 폐기 결과를 삭제 작업에 저장하므로 이후 Auth·데이터 정리 실패와 응답 재전달에서도 결과가 유지된다.

## 상태와 재시도

| 상태 | 뜻 | 앱과 서버의 동작 |
| --- | --- | --- |
| `deleting` | `attempt`가 한 실행을 소유한다. `phase`는 정리 / 카카오 연결 해제 / Auth 삭제 단계다. | 같은 UID의 중복 삭제와 카카오 재로그인을 거부한다. 시간이 지나도 claim을 자동 회수하지 않는다. |
| `retryable` | 실행이 끝난 오류다. 외부 카카오 연결 해제 결과가 불확정인 오류는 여기에 넣지 않는다. | 기존 인증 세션에서 탈퇴를 다시 요청하면 남은 정리를 이어간다. 새 가입은 여전히 거부한다. |
| `blocked` | 카카오 연결 해제 응답을 확정하지 못했다. | 재가입과 자동 재시도를 거부하고 고객지원 확인을 안내한다. |
| `deleted` | 데이터·Auth 삭제와 완료 기록 저장이 끝났다. | 중복 탈퇴는 저장된 결과만 반환한다. 카카오 재가입은 새 UID를 발급한다. |

카카오 연결 해제 실패를 성공으로 삼키지 않는다. 프로세스가 강제 종료되면 `deleting`이 남을 수 있으며, 이는 불확정 상태에서 재가입을 허용하는 것보다 안전한 실패다. 만료된 클라이언트 인증 세션으로는 재시도하지 못할 수 있으므로 이 경우에도 아래 운영 복구를 거친다.

## 운영 복구 절차

1. 운영자는 요청자의 소셜 계정 소유권과 해당 UID를 별도 지원 절차로 확인한다. 현재 `kakaoAccounts`가 다른 세대 UID를 가리키는지도 확인한다.
2. `startedAt`, `phase`, `attempt`와 Cloud Functions 실행 기록을 대조한다. **원래 실행이 종료됐고 외부 연결 해제 요청도 더 이상 진행 중이지 않다는 것을 확인하기 전에는 상태를 바꾸지 않는다.** 단순 시간 경과, 클라이언트 타임아웃, 네트워크 예외는 완료 근거가 아니다.
3. `blocked` 또는 `kakao-unlink` 단계에서 종료된 실행은 카카오의 처리 결과까지 확인한다. 결과를 확인하지 못하면 차단을 유지한다. 결과를 확인하기 전에 새 UID를 발급하거나 매핑을 변경하지 않는다.
4. 실행 종료가 확인됐지만 정리가 남았으면 서버 관리 환경에서 원래 UID의 작업을 `retryable`로 바꾸고, 동일 삭제 경로를 다시 실행한다. 클라이언트에 관리 권한이나 새 세대의 토큰을 전달하지 않는다. 이미 없는 Auth 사용자는 성공으로 처리하며, `deleted`는 전체 정리 후 서버가 기록한다.
5. 완료 뒤 원래 UID의 차단 기록은 유지한다. **차단 문서 삭제, 기존 UID 재사용, 시간에 따른 자동 claim 회수는 금지한다.** 고객이 로그인하면 정상 경로가 새 가입 세대를 만든다.

서버 함수와 Firestore·Storage 규칙을 함께 배포한다. 구버전 삭제 실행이 남아 있는 상태에서 새 로그인 세대를 여는 배포를 하지 않는다. 이 PR 자체는 운영 배포를 수행하지 않는다.

## 검증

`firebase/functions`에서 `npm run test:account:emulator`를 실행한다. demo 프로젝트의 실제 Auth·Firestore·Storage 에뮬레이터만 사용한다. Auth 삭제 직후 중복 요청·재가입, 이전 커스텀 토큰으로 Auth 재생성 후 데이터 차단, 새 세대 보존, 실패 후 재시도, 버려진 claim, 지연된 초대 수락과 Apple 코드 교환을 확인한다. `npm run test:unlink:emulator`는 연결 해제 작업 자체의 중단·중복·새 연결 보존을 확인한다.
