# 관계와 활성 키를 같은 DB 커밋으로 공개하기

## 문제

#148의 기존 연결 완료 순서는 플랫폼 키 저장 → 관계 행 저장 → 두 기기 행 저장이었다. 기기 행 저장이 실패하면 활성 키와 불완전한 관계가 남았다. DB 오류 때 플랫폼 키를 무조건 지우는 보상 작업은 중단 후 복구가 어렵고, 이미 교체된 키를 지울 수 있다.

## 결정

새 연결은 커플 키를 기기 공개키 앞으로 봉인하고 `couple.sealedKeys`에 저장한다. 봉투 안의 관계 ID, 소유 계정, 기기 ID, epoch별 키를 기기 서명으로 검증하고 기기 비밀키로 복호화한다. 관계 행·기기 행·키 봉투를 하나의 SQLite 트랜잭션에서 저장하므로, 커밋 전 종료나 DB 오류에는 공개할 활성 관계·키가 없다. 커밋 후 초대 기록 정리만 실패했다면 재시도는 완료된 관계를 인정하며 이후 교체된 epoch를 되돌리지 않는다.

`CommittedKeyVault`는 현재 관계 행을 키의 기준으로 삼는다. 새 관계의 키가 손상되거나 계정·기기·관계가 다르면 이전 플랫폼 키로 폴백하지 않는다. 기기 비밀키는 계속 Keystore/Keychain에만 있고, DB는 기존대로 OS 백업에서 제외한다. 기기 비밀키를 잃은 DB 사본만으로 키를 복구할 수 없다.

Room v1→v2는 nullable 열 하나를 추가하는 AutoMigration이다. 구버전 관계의 null 값은 기존 플랫폼 키 사용을 뜻하므로 기존 키를 새로 만들거나 지우지 않는다. 새 기기 교체 완료도 같은 봉투를 저장하며, 새 방식 관계의 epoch 교체는 DB에서 키 봉투와 기기·관계 변경을 함께 커밋한다. 연결 해제는 같은 트랜잭션에서 해당 관계의 봉투를 지운다. 이후 플랫폼 보관함 정리가 지연돼도 새 관계의 DB 키는 영향을 받지 않는다.

## iOS 확장

Swift 위젯·NSE는 앱 DB를 열지 않는다. 앱은 커밋된 키를 관계·기기·epoch 식별자와 함께 단일 `relationship.keys` Keychain 항목에 복사하고, 그 다음 같은 식별자의 `link.json`을 게시한다. 두 항목 중 하나만 갱신된 동안에는 식별자 불일치로 확장이 키를 사용하지 않는다. 새 형식의 키가 없을 때 구버전 개별 키를 대신 사용하지 않는다. 앱 재실행·위젯 갱신 시 다시 게시할 수 있으며 DB의 원본 키는 유지된다.

## 검증과 한계

- 실제 연결 경로의 두 번째 기기 INSERT 실패: 관계·두 기기·활성 키 모두 롤백, 같은 초대를 재시도해 완료.
- 파일 DB 재개방 후 키 복구, 관계·계정·기기 변경 및 봉투 손상 거부, 구버전 키 읽기.
- 초대 기록 정리 실패 후 epoch가 올라간 경우 재시도에서 최신 키 유지.
- v1 데이터 보존과 v2 스키마 이전.
- 기기 비밀키 저장 실패는 기존 플랫폼 보관함의 실패 안전 쓰기 계약을 따른다. #131의 전체 탈퇴/해제 단계 복구와 #156의 구버전 iOS 보관함 다중 프로세스 갱신은 별도 작업이다.

v2 DB를 만든 뒤 v1 앱으로 되돌리는 다운그레이드는 지원하지 않는다. 문제가 생기면 데이터를 지우는 대신 v2를 읽는 수정 빌드로 복구한다.
