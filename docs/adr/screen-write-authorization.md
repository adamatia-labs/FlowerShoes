# 화면의 실제 저장 시점에 계정과 관계 재확인

이슈 #131의 이전 화면 작업 경합을 다룬다. ViewModel 취소만으로는 정리가 끝난 뒤 새 관계가 생기고 Compose가 아직 이전 상태를 표시하는 구간을 보호하지 못한다. 실제 WIPE 정리를 마친 뒤 이전 편집기의 새 일정을 저장하면 새 관계에 쓰이는 실패를 재현했다.

## 결정

홈에 진입한 화면은 계정 UID·기기·로그인 세대와 관계 id·소유자·상대·키 epoch·연결 시각을 고정한 `ScreenData`를 사용한다. 각 ViewModel의 Repository, 첨부 저장소, 설정, 신원은 이 화면 범위에서 제공한다. 전역 백그라운드 서비스의 Repository를 교체하지 않는다. 로그인 중 UID가 바뀌는 온보딩은 기존 수명주기를 유지한다.

저장은 DataStore의 실제 계정 잠금 안에서 세대와 정리 예약을 확인하고, Room immediate 트랜잭션에서 정리 행과 현재 관계를 다시 확인한다. 파일 생성도 이 검사 뒤에 수행한다. 계정이 A→B→A로 돌아오거나 정리 행이 이미 지워졌어도 이전 권한은 되살아나지 않는다. 거부는 코루틴 취소로 전달한다.

계정과 관계 Flow의 갱신 시점이 달라도 관계의 소유자 UID는 화면 계정과 같아야 한다. 서로 다른 소유자의 정보를 함께 캡처한 화면은 저장과 삭제 예약을 거부한다. 알림 미리보기 파일 변경도 설정의 같은 권한 검사 안에서 실행하고, 서버 알림 설정은 화면 계정의 UID를 목적지로 고정한다. 서버 전송 직전 인증 UID가 바뀌었으면 요청을 보내지 않는다.

잠금 순서는 DataStore → Room이다. 초안 보내기와 상태 편집처럼 이미 DataStore 잠금 안에서 실행되는 작업은 확인한 실제 계정을 코루틴 컨텍스트에 전달해 같은 잠금을 다시 잡지 않는다. 다른 계정의 초안 보존 경로는 이전 화면에 쓰기 권한을 주지 않는다. 편지 보내기가 별도 신원으로 고정한 writer를 만들 때도 바깥의 화면 권한 검사를 먼저 통과해야 한다.

연결 해제·상대 해제·탈퇴 확인은 화면이 본 계정과 관계를 삭제 예약 대상과 비교한다. 그 이후의 경합은 기존 DataStore 예약과 Room 저널 설치 검사가 처리한다. 복구는 화면과 별개로 저장된 원래 대상을 계속 사용한다.

키 epoch 변경도 화면 범위를 갱신한다. 연결 후처리를 재개할 때는 현재 관계의 epoch를 설정해 이전 완료 안내가 새 키를 1로 되돌리지 않도록 한다.

## 검증

실제 Room/DataStore 테스트로 완료된 WIPE 뒤 이전 새 일정 저장, A→B→A 뒤 설정·첨부 쓰기, 독립 DB 연결의 관계 변경과 지연된 저장, 중첩 상태·기념일·편지 쓰기, 초안 전송의 별도 writer 우회, 다른 계정의 잠금 재사용, 이전 화면의 새 관계 삭제를 확인한다. 거부된 저장은 본문·동기화 로그·첨부 파일·서버 호출을 남기지 않는다.

Android 에뮬레이터에서는 실제 Koin 화면 조립을 사용한다. 이전 화면을 남겨 둔 채 WIPE와 새 관계 생성을 마치면 이전 CalendarViewModel의 저장은 거부되고 새 ViewModel은 정상 저장한다. 전역 Repository 객체도 유지된다. Activity 재생성·계정 전환·취소된 연결 후처리 테스트를 함께 실행하며, 키가 교체된 뒤 미확인 완료 안내가 다시 나타나도 새 epoch를 유지하는지 검사한다.

## 앱의 위젯 발행

앱과 함께 오래 살아 있는 위젯 발행기도 같은 저장 경계를 사용한다. DataStore의 계정 UID·기기·로그인 세대가 바뀌면 집계 구독을 새로 만든다. 시작 시의 신원 캐시를 계속 쓰지 않으며, 계정과 Room 관계의 소유자가 다른 중간 상태는 발행하지 않는다.

각 스냅샷은 집계할 때 확인한 계정과 관계를 함께 전달한다. 파일 교체와 갱신 콜백은 DataStore → Room 검사 안에서 실행하므로 완료된 정리 뒤 이전 결과를 다시 쓸 수 없다. 플랫폼의 위젯 배치 조회는 잠금 밖에서 기다리고, 이후 그림 표시 시간을 기록할 때 같은 세대를 다시 확인한다. 거부된 발행 한 건은 버리고 발행기는 다음 계정의 변경을 계속 구독한다.

실제 Room/DataStore 테스트는 신원 캐시가 이전 계정이어도 새 계정의 보고싶어 횟수로 전환하는지, 배치 조회가 늦게 끝나도 새 계정의 표시 시간을 지우지 않는지 확인한다. Android 위젯 호스트의 렌더링·갱신 회귀도 에뮬레이터에서 실행한다.

## iOS 위젯·알림 확장

앱의 스냅샷과 `link.json`은 같은 `WidgetOwner`를 전달한다. 계정 UID·기기·로그인 세대와 관계 id·상대·키 epoch·연결 시각을 포함한다. 연결 정보 발행도 실제 DataStore → Room 경계를 통과하고, 변할 수 있는 신원 캐시 대신 확인한 계정을 쓴다.

계정 B와 아직 남은 A의 관계가 함께 보이면 실제 계정 잠금 안에서 이전 링크와 스냅샷을 지운다. 연결 해제·상대 해제·탈퇴도 `DATABASE_DONE` 단계에서 이 파일을 지운 뒤에만 `SIDE_EFFECTS_DONE`으로 넘어간다. 보관 선택에도 동일하게 적용한다. 파일 무효화가 실패하면 저널을 남기고 다음 실행에서 재시도하므로, 발행기의 지연이나 앱 종료가 정리 완료 뒤 이전 확장 권한을 남기지 않는다.

보고싶어 전송은 요청을 시작할 때 읽은 소유권을 완료 결과와 함께 돌려준다. 알림 확장도 복호화 전에 읽은 연결 정보의 소유권을 사용한다. 확장이 스냅샷을 수정할 때는 이 소유권과 현재 스냅샷의 소유권이 일치해야 한다. 이전 파일은 표시할 수 있지만 소유권이 없으면 확장 쓰기를 허용하지 않는다.

검사와 파일 교체 사이의 경합은 앱과 확장이 공유하는 `widget/.snapshot.lock`의 `flock`으로 막는다. 잠금 파일 자체는 교체하거나 지우지 않는다. 확장은 잠금 안에서 읽기·소유권 검사·수정·원자적 교체를 수행하며, 앱의 스냅샷 발행과 그림 경로 갱신도 같은 잠금을 사용한다. 네트워크 전송과 복호화는 잠금 밖에 있다. Android 확장은 스냅샷을 읽기만 하므로 추가 프로세스 잠금을 사용하지 않는다.

Swift 파일 테스트는 새 관계·재로그인·키 교체 뒤 이전 완료 결과가 거부되는지, 같은 소유권은 정상 반영되는지, 이전 파일의 표시를 유지하면서 쓰기를 거부하는지 검사한다. 지연된 확장 쓰기와 앱 파일 교체도 동시에 실행해 새 스냅샷이 마지막에 남는지 확인한다. Kotlin 회귀는 실제 계정 전환 때 파일에 전달되는 소유권이 함께 바뀌는지 확인한다.

실제 Room/DataStore 정리 테스트는 새 스냅샷 발행 없이 WIPE·KEEP·탈퇴 완료 직후 파일이 없음을 확인한다. 무효화 실패 후 새 서비스가 원래 저널을 재개하는 경우와 혼합 소유자의 링크 폐기도 검사한다. Swift는 지워진 스냅샷을 지연된 완료 결과가 다시 만들지 않는지 확인한다.

이 경계는 화면·앱 발행기·iOS 확장의 스냅샷 쓰기를 담당한다. 서버 탈퇴 응답 유실 복구와 수신 첨부·본문 검증은 각각의 변경과 함께 #131 전체 완료 여부를 판단한다.
